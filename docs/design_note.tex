\section{Introduction and task framing}
\begin{itemize}
\item Build and compare lexical (BM25) and semantic (embedding) candidate retrieval on MIND (English) and EB-NeRD (Danish).
\item Rank each impression's own candidate list with a shared offline evaluation harness; submit predictions to both datasets' Codabench leaderboards.
\item One pipeline (unified schema, temporal split, feature store, BM25/FAISS retrieval, evaluation), parameterised per dataset rather than duplicated -- deliberately exercised throughout given the datasets' differing language, catalog size, and candidate-list structure.
\end{itemize}

\section{Data pipeline}
\begin{itemize}
\item Unified schema: \texttt{articles} (id, title, abstract/subtitle, category, entities) and \texttt{impressions} (id, user, timestamp, candidates, labels, click history).
\item Splits are \textbf{temporal, not random}: a fixed calendar-day boundary separates train/val, and the provided val/test structure is preserved (MIND: MINDsmall\_train split by day for train/val, MINDsmall\_dev held out entirely for offline test; EB-NeRD: native train/validation windows kept as-is).
\item This matters because random splitting would leak future-clicked articles into a user's ``history'' feature, silently inflating offline metrics relative to what a production system would see. A leakage test asserts every impression's history timestamps precede its own timestamp, on every split.
\item The feature store materialises one \texttt{articles.parquet} per dataset (with train-split click counts, for the popularity cold-start fallback) and one \texttt{users.parquet} per split.
\end{itemize}

\section{Lexical retrieval}
\begin{itemize}
\item BM25 is a hand-rolled sparse CSR matrix (scikit-learn's \texttt{CountVectorizer} used only for tokenise/vocabulary bookkeeping; the BM25 weighting itself, $idf \cdot \frac{tf(k_1+1)}{tf + k_1(1-b+b\cdot L/\bar L)}$, is computed directly into the matrix).
\item \texttt{rank\_bm25} was rejected on a directly measured benchmark, not an assumption: scoring 196 real queries against MIND's 65K-article catalog took \textbf{73.0s} with \texttt{rank\_bm25} (2.7 q/s, one document at a time in a Python loop) vs. \textbf{0.09s} with my CSR matmul (2099 q/s) -- a \textbf{782$\times$} speedup; extrapolated to MIND's full 73K-impression test split, \texttt{rank\_bm25} would need $\sim$7.6 hours vs. my 35s (EB-NeRD: $497\times$ at its smaller 11.8K-article scale).
\item Danish text uses Unicode-aware tokenisation with per-language stopwords (compounding and \texttt{æøå} are not handled by an English pipeline); English MIND titles use a lighter English tokeniser.
\item Whether to additionally \emph{stem} was tested, not assumed: stemming (Snowball) is \textbf{off by default} for both languages, and an ablation shows this is the right per-language default rather than a uniform choice -- stemming measurably \emph{helps} EB-NeRD (B@200 recall $0.0444\to0.0604$, $+36\%$ relative) but \emph{hurts} MIND slightly (B@200 $0.1405\to0.1372$, $-2.3\%$), consistent with Danish's heavier compounding morphology. Not adopted into the scored submission (would cost a rescoring cycle against EB-NeRD's 5/day Codabench cap) but a concrete, measured next step.
\item A query is the concatenation of the titles of a user's last $N$ clicked articles ($N$ swept on validation).
\item Recall@K is reported under \textbf{two candidate pools}: Pool A is the full article catalog (tests true retrieval power) and Pool B is only the impression's own shown/active candidates (tests realistic re-ranking, since a production system typically re-ranks a pre-filtered slate, not the whole catalog). Pool B recall is substantially higher than Pool A at every K, confirming this distinction is not academic:
\end{itemize}

\section{Semantic retrieval}
\begin{itemize}
\item Per an explicit instruction to avoid training or running my own embedding model, retrieval uses only \textbf{provided} article embeddings: MIND ships \texttt{entity\_embedding.vec} (TransE, 100-dim, keyed by WikidataId), mean-pooled per article over its title+abstract entities (87.03\% catalog coverage; articles with no tagged entity have no vector and are excluded from this path); EB-NeRD ships a native word2vec \texttt{document\_vector.parquet} (300-dim, 100\% coverage).
\item Search uses FAISS \texttt{IndexFlatIP} (exact inner product over L2-normalised vectors = cosine similarity), with an equivalent numpy brute-force fallback when \texttt{faiss-cpu} is unavailable: both are exact, so the fallback is not an approximation.
\item A user's query vector is the mean of their last $N$ clicked articles' embeddings, $N$ swept on validation. Val-sweep selected $N{=}1$ for \emph{both} datasets' semantic path (vs. $N{=}20$ for MIND's BM25): a single most-recent click is a better semantic query than an average over a long history, which tends to wash out the user's current interest into a diffuse centroid; BM25's term overlap does not have the same failure mode since additional history terms only add matching opportunities, not dilution.
\item At demo/small scale exact search easily keeps up with offline evaluation ($\sim$1140 QPS for MIND, $\sim$2580 QPS for EB-NeRD at $k{=}200$); see \S7 for why this stops being true at scale.
\item Exact search's headroom against real ANN alternatives was also measured directly, not left as an assumption: against \texttt{IndexFlatIP}'s exact top-100, an \texttt{IndexIVFFlat} (nlist$=\sqrt{n_\text{docs}}$) reaches $91$--$92\%$ recall at nprobe$=8$ while running $13$--$20\times$ faster than exact search (46K vs.\ 3.6K q/s on MIND; 43K vs.\ 2.2K q/s on EB-NeRD); \texttt{IndexHNSWFlat} (M$=32$) reaches a comparable $93$--$99\%$ recall at efSearch$=64$ at $15$--$19\times$ exact's throughput. At demo scale this headroom is unnecessary, but it is exactly the lever \S7 needs at $10\times$+ catalog size, where exact search's $O(n_\text{docs})$ cost per query stops being free.
\end{itemize}

\section{Lexical vs. semantic}
\begin{center}\small
\begin{tabular}{lrrrrr}
\toprule
 & AUC & MRR & nDCG@5 & nDCG@10 & ILD (cat.) \\
\midrule
MIND / BM25 & \textbf{0.554} & \textbf{0.306} & \textbf{0.280} & \textbf{0.342} & 0.843 \\
MIND / semantic & 0.536 & 0.274 & 0.252 & 0.314 & 0.827 \\
EB-NeRD / BM25 & 0.501 & 0.267 & 0.283 & 0.383 & \textbf{0.799} \\
EB-NeRD / semantic & \textbf{0.509} & \textbf{0.325} & \textbf{0.354} & \textbf{0.439} & 0.781 \\
\bottomrule
\end{tabular}
\end{center}
\begin{itemize}
\item BM25 wins on MIND; semantic wins on EB-NeRD, on every accuracy metric. I read this as a \textbf{dataset property, not a general lexical-vs-semantic verdict}: EB-NeRD's word2vec has 100\% coverage and is trained natively on the same Danish news corpus, while MIND's entity embeddings only cover 87\% of articles and represent named entities, not full article semantics: a weaker signal for a language (English) where BM25 already has strong exact term overlap.
\item A second dataset difference shows up in the cold-start slice: MIND's evaluated split has 14\% cold-start impressions (empty click history) vs. \textbf{zero} in EB-NeRD's, since EB-NeRD's provided val/test windows apparently guarantee prior history, while MINDsmall\_dev does not.
\item On MIND's \emph{head} (high-popularity) articles specifically, BM25's MRR (0.412) clearly beats semantic's (0.345), but on EB-NeRD's head articles semantic's AUC (0.551) beats BM25's (0.495) while BM25's MRR (0.433) beats semantic's (0.295): semantic ranks a plausible candidate higher on average (AUC) without as reliably placing the true click first (MRR). A production system on EB-NeRD-like data would plausibly hybridise: semantic for overall ranking quality, with a lexical/popularity tie-break for exact top-1 placement on popular articles.
\end{itemize}

\section{Evaluation harness}
\begin{itemize}
\item Each impression's own candidate list is scored and ranked (a distinct task from \S3--4's catalog-wide recall, since a production ranker only ever re-orders the candidates it was already shown).
\item Metrics: AUC, MRR, nDCG@\{5,10\}, all with seeded bootstrap 95\% CIs (1000 resamples).
\item Beyond-accuracy metrics over each impression's top-10: intra-list diversity (both category-based and embedding-based); novelty via inverse train-popularity with $+1$ smoothing; catalog coverage.
\item Sliced by cold-start/warm and head/tail articles (head/tail split at the 90th percentile of train-split click count; on both datasets over 90\% of articles have \emph{zero} train clicks, so this threshold lands exactly at 0 and needs a strict $>$ comparison, not $\ge$, or every article is misclassified as ``head'').
\item Both submissions are scored on their respective Codabench leaderboards:
\end{itemize}

\subsection*{Q9.1: serving-feature ablation}
\begin{itemize}
\item EB-NeRD only: MIND's unified-schema columns for these features are entirely null (the raw MIND files carry no corpus-aggregate engagement or post-interaction stats), so this ablation is not constructible for MIND at all, not merely skipped.
\item Three cumulative rows, on the same labeled offline test split as \S5--6 (11,798 impressions; the Codabench test sets are blind, with no labels, so this exercise is impossible there regardless of scale):
\end{itemize}
\begin{center}\small
\begin{tabular}{llrrrr}
\toprule
Method & Config & AUC & MRR & nDCG@5 & nDCG@10 \\
\midrule
BM25 & clean (deployable) & 0.501 & 0.267 & 0.283 & 0.383 \\
BM25 & + popularity & 0.576 & 0.360 & 0.400 & 0.475 \\
BM25 & + post-interaction (leak) & \textbf{1.000} & \textbf{1.000} & \textbf{1.000} & \textbf{1.000} \\
Semantic & clean (deployable) & 0.509 & 0.325 & 0.354 & 0.439 \\
Semantic & + popularity & 0.581 & 0.363 & 0.406 & 0.479 \\
Semantic & + post-interaction (leak) & \textbf{1.000} & \textbf{1.000} & \textbf{1.000} & \textbf{1.000} \\
\bottomrule
\end{tabular}
\end{center}
\begin{itemize}
\item ``clean'' uses only the base retrieval score.
\item ``+ popularity'' adds a re-ranking prior from \texttt{total\_inviews}, \texttt{total\_pageviews}, \texttt{total\_read\_time}, \texttt{sentiment\_score} (corpus-aggregate, hence unavailable at serving time: they are computed over the article's whole lifetime, including the future relative to any given impression): a real, meaningful lift on both methods, since popularity genuinely correlates with clicks.
\item ``+ post-interaction'' adds a large bonus directly to whichever candidate is the true click for that impression: the most direct possible post-interaction feature, since the click outcome is exactly the label being predicted. It scores perfectly on every metric, on both methods, by construction.
\item Only the \emph{clean} row is a deployable system; the other two exist to measure the temptation, and the gap between clean and +popularity (roughly +0.07--0.09 AUC, +0.04--0.09 nDCG) quantifies how much of an apparently strong popularity-boosted result would really be leakage rather than retrieval quality.
\item Caveat found while building this: EB-NeRD also ships \texttt{next\_read\_time} and \texttt{next\_scroll\_percentage} on \emph{impressions} (not per-candidate): since AUC/MRR/nDCG are computed from each impression's own relative candidate ranking, a value that is identical across every candidate in an impression cannot move any of these metrics at any weight, so it was not used as a ranking feature; not every ``leaky'' column is exploitable via simple re-ranking.
\end{itemize}

\section{Where it breaks at 10$\times$}
\begin{itemize}
\item I did not have to extrapolate: Q5's real test sets \emph{are} an order-of-magnitude scale jump over dev, and building the submission pipeline surfaced concrete failures.
\item \textbf{EB-NeRD}: demo (11.8K articles, 24.7K impressions) $\to$ \texttt{ebnerd\_testset} (125.5K articles, \textbf{13.5M} impressions: 548$\times$ more impressions, 10.7$\times$ more articles).
\item \textbf{MIND}: MINDsmall (65K articles, 73K impressions) $\to$ MINDlarge\_test (121K articles, \textbf{2.37M} impressions: 32$\times$, 1.9$\times$).
\end{itemize}
Three real breakages, found in that order, each traced to a specific mechanism and fixed:
\begin{enumerate}
\item \textbf{Unrestricted parquet loads $\to$ OOM.} Reading the full \texttt{behaviors}/
\texttt{history} parquet files (many unused columns: device type, scroll \%, session id, three
extra per-user history-list columns) into pandas before any batching hit \textbf{10.5GB RSS} and
was killed by the OOM killer (15GB machine, $\sim$8.6GB free). Fix: column-prune at the parquet
reader (only the $\sim$4 columns actually used) and stream \texttt{behaviors} in batches instead
of materialising all 13.5M rows $\to$ peak RSS \textbf{1.7GB}.
\item \textbf{$O(\text{batch}\times\text{catalog})$ dict construction.} Building a
\{article\_id: score\} dict over the \emph{whole} 125K-article catalog for every one of 13.5M
impressions (each of which only has $\sim$12 real candidates) was estimated at \textbf{70+ hours}
of pure dict-construction, separate from the actual scoring math. Fix: restrict output extraction
to each batch's own candidate IDs via a precomputed id$\to$column index.
\item \textbf{Full-catalog score matrix.} Even after (2), computing the full
(batch$\times$125K) dense similarity matrix per batch was still $\sim$\textbf{10 hours}
end-to-end (measured: 367 impressions/sec). Since matrix columns are independent, restricting the
matmul itself to only each batch's $\sim$250--300 unique candidate columns (not the full 125K) is
numerically \emph{identical} (verified: max diff $1.8\times10^{-7}$, pure float32 rounding, not
an approximation), and dropped the run to \textbf{49 minutes} (4629 impressions/sec).
\end{enumerate}
\textbf{Correction (re-measured):}
\begin{itemize}
\item The original write-up blamed the 10-hour run partly on ``OpenBLAS capped at 2 threads'' (from \texttt{numpy.\_\_config\_\_.show()}'s \texttt{MAX\_THREADS=2} build field).
\item A direct \texttt{OPENBLAS\_NUM\_THREADS} sweep on the real matmul shape ((500,100)$\times$(100,56774)) shows that field is \emph{not} an enforced ceiling: throughput keeps improving past 2 threads (180$\to$95$\to$52$\to$52ms at 1/2/4/8, plateauing at 4; confirmed with a bare numpy benchmark too).
\item That claim is retracted -- the real bottleneck was purely the $O(\text{batch}\times\text{catalog})$ matrix size (fixed by optimization 3), not thread count.
\item By contrast BM25's \emph{sparse} \texttt{Qmat @ W.T} scoring (\S3) shows \emph{no} thread sensitivity (flat $\sim$2150 q/s on MIND, 1--8 threads): scipy's sparse matmul skips the threaded dense-BLAS path numpy's \texttt{@} uses, so the two needed separate benchmarks rather than a shared assumption.
\end{itemize}
\begin{itemize}
\item Applying all three fixes \emph{preemptively} to MINDlarge\_test (2.37M impressions) produced a clean first-try run: 0.83GB RSS, 2019 impressions/sec, $\sim$20 minutes.
\item A fourth, unrelated failure: downloading \texttt{ebnerd\_testset.zip} (1.6GB) over a single TCP connection crawled at 15--30KB/s with repeated stalls (confirmed via packet loss on the route, independently on two networks), even though the same link hit 1.5MB/s to a different host: a single flow's throughput is capped by loss$\times$RTT, not by the physical link's capacity. Splitting the download into 24 parallel range-requested connections against the same object raised effective throughput $\sim$30$\times$.
\end{itemize}
\textbf{Extrapolating past 13.5M}:
\begin{itemize}
\item EB-NeRD's full production data is $\sim$600M impressions ($\sim$44$\times$ beyond what I stress-tested).
\item Even the fixed scoring loop (4629--4949 impressions/sec) would need $\sim$36 hours to process 600M rows, since the per-impression Python loop (rank-sorting, dict lookups) itself becomes the bottleneck once the matmul is no longer dominant -- needing either sharding across processes/machines or a fully vectorised batch rank operation.
\item BM25's \texttt{.todense()} step (exercised at MIND's 2.37M scale, where it worked) would need the same candidates-only restriction at EB-NeRD's full scale.
\item Article-serving embeddings stay fine at 10$\times$ catalog size ($\sim$1.5GB) but need row-group streaming at 100$\times$.
\item A client-side parallel downloader is a workaround, not a fix: at 10$\times$ volume a bad network path needs a regional mirror or shared pre-staged storage, not more connections.
\end{itemize}

\section{Limitations and references}
\begin{itemize}
\item Single-node, CPU-only; embeddings are provided-only by instruction, trading representation quality for zero training cost and full reproducibility.
\item The IVF/HNSW recall-vs-latency curve (\S4) was measured at demo/small scale only, not at the $10\times$+ production catalog sizes \S7 discusses.
\item Cold-start fallback is train-split popularity only.
\item MINDlarge\_test is genuinely blind (no labels), so submission quality is only checked structurally offline, not validated against ground truth until scored by Codabench.
\end{itemize}
